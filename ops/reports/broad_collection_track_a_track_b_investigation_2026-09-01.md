## トラックB: approach_value判定の頑健性調査（read-only）

### 1. 判定ロジックの所在と内容

[scripts/x_api_phase2_classify.py](../../scripts/x_api_phase2_classify.py)の`_observe()`内（`approach_value`算出部）:

```python
approach_signals = sum([
    decision_hits > 0,                    # DECISION_KEYWORDS（26語）+トレンド語補正のヒット数>0
    usefulness in ("medium", "high"),     # usefulness = level(decision_hits + (utility_hitsが1件以上なら+1))
    has_aesthetic and has_utility,        # AESTHETIC_KEYWORDS（20語）とUTILITY_KEYWORDS（10語）が両方ヒット
    has_age and has_aesthetic,            # AGE_KEYWORDS（9語）とAESTHETIC_KEYWORDS（20語）が両方ヒット
])
approach_value = "high" if approach_signals >= 3 else ("medium" if approach_signals >= 2 else "low")
```
`aggregator_dominant`（集約bot判定）の場合は無条件で`"low"`に強制される。

**事実**: 4条件のうち1つ目（`decision_hits>0`）と2つ目（`usefulness in medium/high`）は、`usefulness`の算出式自体が`decision_hits`を内包しているため、`decision_hits>0`の投稿は自動的に両方の条件を満たす（実質的に独立した4条件ではなく、"decision語あり"1条件＋"aesthetic×utility共起"1条件＋"age×aesthetic共起"1条件、の3条件に近い）。

### 2. 定量的な厳しさの評価

依存辞書サイズ: `DECISION_KEYWORDS`=26語、`UTILITY_KEYWORDS`=10語、`AESTHETIC_KEYWORDS`=20語、`AGE_KEYWORDS`=9語。

トラックAの実データ（88件、代表として追加収集1回分）での実測通過率:

| 条件 | 通過率 |
|---|---|
| `decision_hits > 0` | 11/88 = 12.5% |
| `usefulness in (medium, high)` | 15/88 = 17.0% |
| `aesthetic AND utility` 両方ヒット | **0/88 = 0.0%** |
| `age AND aesthetic` 両方ヒット | 3/88 = 3.4% |
| **`approach_value == "high"`（総合）** | **0/88 = 0.0%** |
| `approach_value in (medium, high)` | 14/88 = 15.9% |

**所見（事実→評価を分離）**:
- 事実: `aesthetic AND utility`の同時ヒットは実データ88件中**1件も発生しなかった**。この条件を満たさない限り、`decision_hits>0`（12.5%の投稿）と`age AND aesthetic`（3.4%の投稿）の重なりだけでは`approach_signals>=3`に届きにくく、結果として**`approach_value=="high"`は実データ上ほぼ到達不可能**になっている。
- 所見: これは意図的な「厳格な閾値設計」というより、**「見た目の審美語」と「実用機能語」を同一の短い投稿内で同時に使う日本語の書き方が実際には稀である」という、実際の文章パターンとの不整合（キャリブレーション不足）の可能性が高い**。厳格さ自体が目的だったのか、単に組み合わせ条件の設計時に実データでの共起率を検証していなかったのかは、設計文書からは確認できなかった（下記4.参照）。

### 3. 実例確認（topic_fit=="high" かつ approach_value!="high" の9件全件）

トラックAの実データから該当9件の投稿本文を全件確認した。

| # | 内容 | 主観評価 |
|---|---|---|

### 4. approach_value導入の経緯

`git show 3cdc1fd:scripts/x_api_phase2_classify.py`（2026-08-16の唯一の関連commit）を確認したところ、**現行と同一の`approach_signals`計算式（4条件、閾値>=3/>=2）が既にこの時点で存在**していた。`ops/reports/`配下を全文検索したが、この特定の計算式・閾値を導入した経緯・意図した通過率を説明する専用の設計文書は見つからなかった（`negation`・`trend false positive`・`三層探索方針`等、他のPhase 2改修は個別のops/reports設計文書を伴っているのに対し、`approach_value`の4条件・閾値設計にはそれが無い）。`ops/reports/manual_review_review_2026-08-15.md`に類似の`approach_reusability`という語があるが、これは人間が手動評価する別概念（value-transfer-card方式の一部）であり、コード内の`approach_value`計算とは無関係。

**所見**: `approach_value`の閾値設計は、他のPhase 2改修と異なり、独立した設計文書・実データでの通過率検証を経ずに導入された可能性が高い。

## 統合所見

- **母数不足かapproach_value厳格さか**という当初の二択について、今回のトラックAの実行方法（連続再実行）では「母数不足」側の検証ができなかった（同一データが返り続けたため）。したがって**母数不足が原因である可能性を否定も肯定もできていない**。
- **approach_value側については、明確な定量的偏りを確認した**: `aesthetic AND utility`共起条件が実データで0%しか発生しておらず、この条件が事実上`approach_value=="high"`への到達を封じている。これは「厳格すぎる」と評価しうる具体的根拠である。ただし実例確認では、この厳格さによって明確に損をしている投稿は9件中1〜2件程度で、残りは概ね妥当にフィルタされていた。
- 総合すると、**「両方が原因」という結論が最も正確**: (1) 広域クエリでの母数がまだ日単位で増えていない（今回未検証）ことに加え、(2) `approach_value`の`aesthetic×utility`条件が実データとかみ合っておらず`"high"`到達をほぼ封じている、という2つの要因が重なっている。ただし(2)の影響は「良質な候補の取りこぼし」レベルであり、「システムが機能不全」とまでは言えない（`"medium"`到達自体は15.9%あり、`approach_ok`（medium以上）は満たしうる。実際に0件だったのは`topic_fit=="high"`との**両立**が起きなかったため）。

## 未解決事項・要判断事項

1. **時間を空けた収集での再検証が必要**: 連続実行では母数不足仮説を検証できなかった。日をまたいだ収集を別途実施する必要がある。
2. **`aesthetic AND utility`条件の見直し要否**: 実データで0%しか共起しない条件が"high"到達をほぼ封じている。この条件式（またはUTILITY_KEYWORDS/AESTHETIC_KEYWORDSの語彙拡充）を見直すかどうかは人間の判断が必要（本調査はread-onlyのため未実施）。
3. **approach_value自体の専用設計文書が存在しない**: 導入時の意図した通過率・厳格さの目標値が不明なため、「現状が意図どおりか」を判断する基準がそもそも無い。人間が意図を確認するか、新たに基準を定める必要がある。
