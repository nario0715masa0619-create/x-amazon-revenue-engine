# provisional_evaluation_phase_2026-08-04.md — Phase 1 暫定評価フェーズ設計

> **位置づけ**: Phase 1（acquisition mode）は現在、次の5〜10投稿を対象とした**評価期間**にある。この期間の目的はX APIへの課金判断を材料に基づいて行うことであり、スクリーンショット起点の数値回収は**この評価期間専用の暫定レーン**である。**恒久的な本番運用ルールとして固定しない。** X API collector（[scripts/x_metrics_collector/](../../scripts/x_metrics_collector/)）は削除せず、将来の有料オプション候補としてコードのまま温存する。
>
> 今は「X APIを使わない」と決めたわけではない。**ROI判断を、実際に数投稿分の証拠が集まるまで意図的に後ろ倒ししている状態**である。

---

## A. 暫定評価フェーズの明文化

- **今は評価期間である**: 次の5〜10投稿を対象に、数値回収の完全性が実際にPDCAへ影響するかどうかを見極める
- **スクリーンショット運用は暫定レーンである**: 人間が見えている数値を1枚のスクショで渡し、AIが見えた値だけ`metrics_24h`に記入する。これは評価期間中の暫定運用であり、Phase 1の恒久ルールにはしない
- **X APIは将来の有料候補である**: `scripts/x_metrics_collector/`のコードは維持するが、現時点では正式レーンとして起動しない。課金判断が下りた場合にのみ再評価・有効化を検討する

切り分けたい問い（このフェーズの存在理由）:
1. より完全なX指標があると、翌日の意思決定は実際に変わるのか
2. X APIがないことで、PDCAの速度や質は本当に大きく落ちるのか
3. 現時点の主ボトルネックは、数値回収ではなく上流の戦略・コピー設計ではないか
4. 数投稿回したあとに、X API課金は投資対効果に見合うか

---

## B. X API課金判断基準

| # | 判断軸 | 見る証拠 |
|---|---|---|
| 1 | より完全な指標が実際に翌日判断を変えるか | 評価期間中、スクショで見える範囲のデータだけでgrowth-strategistが「今日変える1変数」を確信を持って決められたか、それとも判断保留になった日が多いか |
| 2 | `impression_count`だけでも十分に学習が進むか | growth-strategist/council-chairが、impression_count中心の情報だけで妥当な仮説修正ができているか |
| 3 | likes/replies/bookmarks/profile clicksがないと分析が止まるか | performance-analystの週次分析が、これらの欠損で「参考値にすらならない」レベルまで劣化しているか、大まかな傾向は読み取れているか |
| 4 | スクショ運用の摩擦が大きすぎるか | 人間がスクショを撮って渡す手間が、実際に運用を圧迫しているか（提出忘れ・遅延の頻度、負担感） |
| 5 | 上流課題のほうが支配的ではないか | needs_revision発生率、フック仮説の的中率、テーマ選定のズレなど、上流（テーマ設計・フック・競合観測・ターゲット適合・Morning Strategy Briefの質）の問題点の方が投稿パフォーマンスへの影響が大きいと考えられる兆候があるか |

**判断の傾き方（目安、機械的な閾値ではない）**:
- 軸1〜3で「データ不足が明確に意思決定を妨げている」証拠が複数回観測される → 課金の方向に傾く
- 軸5で「上流の問題の方が明らかに支配的」という証拠が観測される → 課金を後回しにして上流改善を優先する方向に傾く
- どちらとも言えない → 評価継続（サンプルを増やす）

## C. 次の5〜10投稿で集めるべき証拠

評価期間中、投稿ごとに以下を記録する（`daily_brief.md`または本ドキュメントの追記運用を想定。厳密な専用シートは今回新設しない）:

1. スクショで見えた項目・見えなかった項目（毎回何が見え何が見えないか、パターンを把握する）
2. その投稿の翌朝、growth-strategistが「今日変える1変数」を確信を持って決められたか、それとも「データ不足で判断保留」になったか
3. Morning Strategy Briefの`Confidence`が`low`／`insufficient evidence`になった回数と、その理由が**データ欠損由来**か**そもそも上流の仮説が弱いから**かの切り分け
4. 実際に反応が悪かった／良かった場合、その要因をテーマ／フック／ターゲット適合の問題として説明できたか、それとも「数字が見えないから分からない」で終わったか
5. スクショ提出にかかった手間（定性でよい。「毎回忘れずにできたか」「面倒だと感じたか」）
6. 事後に「もしAPIで完全なデータがあったら、この日の判断は変わっていたか」を自己評価する（**単にログが綺麗になるだけ**なのか、**実際に意思決定が変わる話**なのかを分離する）

評価期間終了時（5〜10投稿到達時）、上記の蓄積をもとにB節の判断軸に沿って振り返り、G節の3択で結論を出す。

## D. 暫定レーンと将来レーンの分離

| | 暫定評価レーン（現在有効） | 将来のX APIレーン（現在は保留） |
|---|---|---|
| データ取得手段 | 人間が見えている数値のスクショを1枚渡す | X API（`scripts/x_metrics_collector/`） |
| 記入方法 | AI/Claude Codeが見えた値だけ`metrics_24h`に記入 | collectorが自動取得・upsert |
| 網羅性 | 見えている範囲のみ（通常はimpression中心） | public + non-public（User Context次第）で網羅的 |
| `data_quality` | `manual`を基本とする（E節参照） | `ok`/`partial`/`auth_missing`/`api_error`/`url_unresolved` |
| 位置づけ | **Phase 1評価期間の正式な暫定運用** | コードとして温存するのみ。正式運用ではない |
| 起動条件 | 毎投稿（当面継続） | 課金判断が下りた場合にのみ再評価・有効化を検討 |

**この2レーンを文書上・運用上で混同しないこと。** 特に`data_quality`の意味は両レーンで由来が異なるため、記録時にどちらのレーンかを`notes`で明示する（E節参照）。

## E. オペレーター向けの暫定ルール（スクショ運用）

- 見えている数値だけ記入する（推測・補完・0埋めをしない）
- 見えない値は空欄のままにする
- 例: impressionしか見えなければ`impression_count`のみ記入し、他は空欄のまま
- `data_quality`は**`manual`**を設定する
  - `partial`ではなく`manual`を使う理由: `partial`はX API collectorが「publicのみ自動取得できた」場合の値として既に予約されている（[x-metrics-collector.md](../../.claude/agents/x-metrics-collector.md)参照）。スクショ由来の行を`manual`にしておくことで、将来collectorを有効化した際にこの評価期間中の行を誤って上書きさせない（collectorは`data_quality: manual`の行を上書きしない設計に既になっている）
  - 見えた範囲が多い・少ないの違いは`data_quality`ではなく`notes`と「どの列が埋まっているか」で表現する
- `notes`に「スクショ確認ベース」である旨と、見えた範囲（例: 「impressionのみ視認」）を残す
- `checked_at`はスクショを確認した日時、`check_window`は`24h`のまま

---

## F. Morning Strategy Brief側の暫定ルール（不完全データの扱い）

- `impression_count`しかない場合、その投稿・テーマ全体を「失敗」と断定しない（データが薄いことと成果が悪いことを混同しない）
- 指標欠損時は、KPIの断定より**フック仮説の検証**（hook_strengthの観点）を優先する
- データが弱い日は、growth-strategistの`confidence`を`low`にし、`insufficient evidence`の旨を明記する
- 「Yesterday status summary」には、参照した`metrics_24h`行の`data_quality`が`manual`（暫定評価レーン由来）であることを明記し、将来のAPI由来データ（`ok`/`partial`）と混同しない

---

## G. 最終判断フレーム（評価期間終了後）

評価期間（5〜10投稿）終了後、次の3択のいずれかで結論を出す。判断者は人間（最終承認者）。performance-analyst／growth-strategistがB節・C節の証拠を整理し、人間が選ぶ。

1. **今すぐX APIに課金する** — B節の軸1〜3で、データ不足が意思決定を明確に妨げていたと言える証拠が複数観測された場合
2. **まだ評価継続する** — 証拠が不十分、サンプル数が少なすぎる、または判断が割れる場合。次の5〜10投稿バッチで評価を継続する
3. **上流ボトルネックが大きいため、まだ課金しない** — B節の軸5で、上流（テーマ選定・フック・ターゲット適合・Brief品質）の問題の方が明らかに支配的で、数値の完全性を上げても改善に直結しないと判断される場合。この場合はresearcher/marketer/copywriterの精度向上、morning-strategy-councilの検証を優先する
